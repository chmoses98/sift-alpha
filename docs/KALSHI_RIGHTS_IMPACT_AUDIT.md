# Kalshi rights impact audit (RESEARCH_ONLY)

Status: **RESEARCH_ONLY**. This is a read-only audit done on 2026-11-13 against branch `claude/provider-licensing-research-k7d0tj` (main at `a7be4d8`). It is not legal advice.
No network fetch was made and Kalshi was not contacted. No workflow, schedule, registry, code or data file was changed. **None of the containment actions in section 3 have been carried out.** All of them need the owner's approval.

The terms quoted below are recorded verbatim in `docs/PROVIDER_LICENSING_EVIDENCE.md` under "Revision 2": Kalshi Developer Agreement v1.1 and the Kalshi Data Terms of Service. The references used here are:
DA §3 (API use is limited to "facilitating a members own trading on the Exchange"), DA §3.1 (no collecting, caching, aggregating or storing except to facilitate your own trading, and no sharing with third parties), DA §3.5 (no benchmarking or competitive purposes), DA §4.1.1 (the user must be a Member), and DT (Data Terms: personal, non-commercial use only; no collecting, compiling or text-and-data mining; no analysis; no ML or AI use).

## 1. Summary

- **Endpoints used.** Every Kalshi access in this repo uses the **unauthenticated public Trade API v2** at `api.elections.kalshi.com/trade-api/v2`. No Kalshi key or secret name appears in any workflow or in the code. The only key-like variable is `KALSHI_BASE_URL`, a test override.
  Authenticated `/portfolio/orders` and `/portfolio/fills` calls are made by the sibling repo `chmoses98/kalshi-bet-router`, according to `research/audit/clv/live_execution_evidence.json`. That suggests the owner trades on their own Kalshi account. This is relevant to DA §4.1.1 and to the "own trading" scope, but membership was not verified.
- **Scheduled jobs that touch Kalshi data.** Three workflows on `main` have a cron trigger and touch Kalshi data:
  - `shadow-ledger.yml`: hourly, and it loops every 10 minutes.
  - `nfl-prospective-ops.yml`: dated NFL-window crons. Scheduled capture is gated, and the gate was last observed closed.
  - `pages.yml`: every 6 hours. It publishes the dashboard.
  It cannot be confirmed locally whether these actually run, because run history and remote data branches are not visible. Everything else that touches Kalshi data is manual (`workflow_dispatch`) or a CLI, or runs offline in CI.
- **Kalshi data committed to git.** Raw or near-raw Kalshi data is committed to this repository. The repo appears to be public: `docs/COST_POLICY.md` says "the public repository", and there is a GitHub Pages deploy. Visibility was not verified over the network. The committed data includes:
  - verbatim contract rules text for 2,772 series;
  - series metadata for 4,156 series;
  - a per-contract bid/ask/volume CSV with 2,313 rows;
  - candle-derived per-market samples.
  Workflows also push Kalshi-derived data to the `shadow-data` and `sweep-data` branches, and to `prospective-data` through the lab code.
- **Model training.** No model is trained on Kalshi prices. `alpha_engine/input_research/marketfree.py` enforces a market-free input policy, and `kalshi_quotes.py` marks quotes as evaluation-only.
  However, Kalshi prices and settlements are used heavily for **evaluation, backtests, calibration, execution studies and rule search**. That is analysis, and arguably benchmarking (DT "analyze" and ML clause; DA §3.5). The fit is especially poor where the purpose is research or publication rather than placing the owner's own orders.
- **Registry status is stale.** `rights_registry.json` and `map.json` still record Kalshi as `UNRESOLVED_INTERNAL_ONLY` "terms unread". `map.json` also says `tos_risk: "low"` and gives the Kalshi datasets the plan class `A_HISTORICAL_BACKFILL_NOW`. Revision 2 of the licensing evidence now rates Kalshi as **"Prohibited by primary text" absent written authorization**.

## 3. Proposed containment actions

These are proposals only, in priority order. **None has been carried out.** Each needs the owner's approval.

1. **Confirm scope with counsel first.** Check that the owner is a Kalshi Member (DA §4.1.1), and whether DA §3's "facilitating your own trading" covers private research that informs the owner's own orders. If it does, most private uses (items 1, 2, 7, 8, 11) may be defensible. Publication and redistribution (items 3, 4, 5, 6, 10) would still fall outside it.
2. **Pause or gate the scheduled collectors.**
   - Disable the `shadow-ledger.yml` cron and stop its successor self-dispatch.
   - Keep the `nfl-prospective-ops.yml` capture gate closed, and consider closing the refresh gate (`ci/GHA_REFRESH_ENABLED`) until scope is confirmed.
   - Check the actual run history in the Actions UI.
3. **Stop publishing Kalshi-derived content.**
   - Pause the `pages.yml` 6-hourly deploy, or strip Kalshi prices, rules text and experiment results from the build.
   - Consider making the repo and its data branches (`shadow-data`, `sweep-data`, `prospective-data`) private.
4. **Quarantine committed Kalshi data.** Move items 3, 4, 6, 7 and 10 (rules text, series snapshot, contracts CSV, sweep results, samples) out of the public tree. Note that removing them from HEAD leaves them in git history. Rewriting history is a separate owner decision.
5. **Freeze new Kalshi collection and analysis.** Treat ML and AI use of Kalshi data as prohibited (DT), including feeding Kalshi Data to AI agents. Keep the market-free policy, and do not start new Kalshi-benchmark experiments.
6. **Update the registries.** In `rights_registry.json` and `map.json`, set Kalshi to `PROHIBITED_ABSENT_WRITTEN_AUTHORIZATION`, set `tos_risk` to high, and remove `A_HISTORICAL_BACKFILL_NOW`, citing Revision 2.
7. **Seek written authorization from Kalshi** (DA §3.1 and DT allow it by written consent) for research storage, benchmarking and any publication, or for a data licence.
8. **Review the sibling repos**, which are outside this audit: `nfl-edge-finder` `market-data` (the bulk Kalshi capture), `kalshi-bet-router`, and the edge-finder archives that this repo reads.

## 4. Uncertainties

- **API vs website terms.** It is unclear whether the website Data Terms govern data obtained through the API, or only DA §3 applies. If only DA applies, the explicit ML prohibition may not reach API data, though §3.1 and §3.5 still would.
- **"Own trading" scope.** It is unclear whether "facilitating your own trading" covers the member's own research, modelling and execution studies that inform their own orders. The `kalshi-bet-router` portfolio calls suggest real own trading, but membership and the link between this research and actual orders are unverified. This audit does not assume either reading.
- **Rules text read by hand.** It is unclear whether reading settlement rules text by hand, to define what a model forecasts, is "use". Bulk programmatic copying (item 3) clearly goes further than reading by hand.
- **Repo visibility.** The repo is inferred to be public from `COST_POLICY.md` and the Pages deploy, but this was not verified over the network. The same applies to the data branches.
- **Running state.** Whether the scheduled jobs actually ran, and the current state of the `prospective-data` gate files, cannot be seen from this clone. The `feat/sift-lab` lab code was not inspected. `nfl-prospective-ops.yml` also refers to a non-Actions "primary capture writer", which is not identified.
- **Indirect sources.** Many uses read Kalshi data indirectly from the owner's own archives in other repos, not from Kalshi directly. This does not change the source licence, but it does change which repo holds the collection.
